# RBAC complet : rôles, permission sets et permissions — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Mise à jour du 2026-11-06 :** la MFA et la reconfirmation sont reportées. Ignorer toute mention de `StepUpRequired` dans ce plan : elle sera ajoutée au retour de la MFA.

**Goal:** Remplacer les droits attribués un par un aux admins par un RBAC administrable (permission → set → rôle → utilisateur), étendu aux utilisateurs normaux, sans modifier l'accès de personne au déploiement.

**Architecture:** Le catalogue de permissions reste dans le code ; les sets, rôles et attributions vivent en base. Les droits effectifs sont l'union des rôles, des sets et des droits directs existants, mis en cache dans Redis. `user.role` reste le niveau d'accès au panneau (`user`, `admin`, `superadmin`) ; le superadmin garde son contournement.

**Tech Stack:** FastAPI, SQLAlchemy async, Alembic, Redis, WebSockets ; Next.js 16, React Query, Zustand, i18next (`en`, `tr`), Vitest, Playwright.

**Spec:** les décisions ci-dessous, prises le 2026-11-06, tiennent lieu de spécification.

**Dépendance:** à exécuter après `2026-11-06-admin-securite-audit.md`, qui fournit `users:unlock`, `users:mfa_reset`, `StepUpRequired` et l'audit avant/après.

## Décisions

- Le RBAC couvre les utilisateurs normaux et l'administration.
- Une personne peut avoir plusieurs rôles et des sets supplémentaires.
- Pas de droit « interdit » : les droits s'additionnent.
- Le périmètre par client est reporté. Aucune colonne ni logique de périmètre maintenant.
- Une permission n'entre au catalogue que lorsqu'une route la contrôle. `users:create`, `users:export`, `activities:export`, `data:*`, `system_health:read` et `jobs:*` arriveront avec leurs fonctions, en phases 2 et 3.

## Global Constraints

- Dépôts Git distincts : `backend/` et `frontend/`. Créer `feat/rbac` dans chacun. Ne pas committer les fichiers modifiés hors plan (`.gitignore`, `graphify-out/`).
- Backend : couches `api → services → repositories → models`, fonctions pures, aucun service n'appelle un autre service, `Depends()` uniquement dans les routes, messages centralisés, docstrings en anglais.
- Tests backend sur SQLite : pas de SQL propre à PostgreSQL hors migrations.
- Migrations réversibles. Les scripts SQL de `database/` sont régénérés en fin de plan.
- Frontend : exports nommés, appels via `src/lib/api/`, textes en `en` et en `tr`.
- Le socle reste hors RBAC : `/auth/*`, `GET /users/me`, `/users/me/events`, `/users/me/sessions*`, `DELETE /users/me`, `POST /users/me/reactivate`, `/settings/public`, `/announcements/active`.
- Après chaque tâche : `graphify update .` dans l'application modifiée.

## Review Focus

- Un admin délégué avec `admins:write` qui vise un superadmin, ou s'attribue une permission qu'il n'a pas : refus (tests tâches 5 et 6).
- Un compte déjà connecté dont le rôle change : effet immédiat, sans reconnexion, y compris sur un canal temps réel ouvert (test tâche 4).
- Redis indisponible : les droits sont lus en base, sans jamais accorder par défaut (test tâche 3).
- Un rôle ou un set système renvoyé modifié par l'API : refus, et le contenu est rétabli au démarrage (tests tâches 2 et 6).
- Une attribution expirée : elle cesse de compter sans action ni redémarrage (test tâche 3).

**Interfaces:**
- Routes :
  - `GET /admin/rbac/permissions` (`roles:read`) : clé, ressource, action, public.
  - `GET|POST /admin/rbac/permission-sets`, `GET|PATCH|DELETE /admin/rbac/permission-sets/{id}` (`permission_sets:read|write`).
  - `GET|POST /admin/rbac/roles`, `GET|PATCH|DELETE /admin/rbac/roles/{id}` (`roles:read|write`).
  - `GET /admin/users/{id}/access` (`users:read`) : `{ roles, permission_sets, direct_permissions, effective: [{permission, sources: [{kind, key}]}] }`.
  - `PUT /admin/users/{id}/roles` et `PUT /admin/users/{id}/permission-sets` (`users:write`) : `{ assignments: [{ id, expires_at }] }`, remplacement complet.
- `ResourceType` gagne `ROLE` et `PERMISSION_SET`.
- Règles, chacune avec son message dédié :
  1. Élément système : modification ou suppression refusée (403).
  2. Rôle ou set encore attribué ou utilisé : suppression refusée (409).
  3. Public respecté : `permissions_allowed_for`, et un rôle n'inclut que des sets de son public (422).
  4. `ensure_can_grant` sur tout contenu créé, modifié ou attribué.
  5. Un compte garde au moins un rôle de public `user` (400).
  6. Cible superadmin : refus (403).
  7. Attribuer un rôle ou set `admin` à un compte `user` exige `admins:write` et `StepUpRequired`, et passe `user.role` à `admin`.
  8. Retirer le dernier rôle, set ou droit direct `admin` repasse le compte à `user`, sauf si `is_last_active_admin`.
  9. Chaque mutation journalise `before` et `after`, invalide le cache et publie `PERMISSIONS_UPDATED`. Pour une modification de rôle ou de set : `invalidate_all_permissions()` et publication, par lots, à chaque compte concerné.
